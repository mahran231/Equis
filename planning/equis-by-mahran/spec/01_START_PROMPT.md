# Paste into Claude Code

Build an original EQUIS BY MAHRAN public website and private coaching web application from scratch using the specification files in this folder. The package is self-contained product direction, not a claim that any application already exists or passes tests. Do not refer to competitor websites, copy competitor code/assets, or depend on an earlier app repository. Do not change any existing EQUIS deployment.

Read every numbered Markdown file and requirements.json. Then:
1. Report the files read, business scope, trust boundaries, unresolved decisions and proposed directory structure. Mark this as planning, not completion.
2. In a new empty project directory, recommend and pin a mutually compatible stable Next.js App Router, React, TypeScript, Supabase, Playwright and unit-test toolchain. Verify current documentation and runtime support. Record exact versions and lockfile. Do not blindly install latest into a preexisting project.
3. Implement in the phases in 06_BUILD_PLAN.md only after the owner tells you to start implementation. The request for this package does not itself authorize production deployment, paid resources, account creation, production migrations or real client-data imports. Local development and synthetic fixtures are the default once implementation is approved.
4. Preserve every requirement ID. Create TRACEABILITY.md mapping each to route, service, migration and test. New product features need owner approval; secure validation and error handling are not optional extras.
5. No fake functionality: buttons must perform the specified action or explain the actual unavailable prerequisite. No placeholder prices, invented credentials, public client photos, hardcoded admin passwords or fake completion charts. Synthetic development records must be visibly marked TEST and excluded from production builds/seeding.
6. Apply database RLS and server authorization to every private operation. A hidden button or route guard is never authorization. Never expose Supabase secret/service-role keys, database credentials, VAPID private keys, mail credentials or tokens in browser bundles, logs, screenshots, prompts or commits. Use local secret files ignored by git or the deployment secret manager; do not ask me to paste them in conversation.
7. Before every write that affects an external system, present destination/environment, effects, reversibility and cost, and obtain the applicable approval. No permission bypass flags, destructive resets, force pushes, broad access policies or silent production migrations.
8. Test as client A, client B, coach A, unrelated coach B, disabled user and anonymous visitor. Call APIs directly to prove denied access, including storage and PDF URLs. Do not use administrator credentials for negative authorization tests.
9. Render and inspect Arabic RTL/English LTR screens and PDF pages. Test 320/390/768/1280px, keyboard access and iPhone Safari on a physical device. Browser emulation is not a substitute for physical push/download/upload tests.
10. At each phase report: changed files, migrations, commands actually run, test results, evidence paths, failures, unresolved decisions, next phase and whether anything was deployed. Never label a requirement complete based on code presence alone.

Start with the read-only plan and decision register. Continue independent work while owner decisions are pending. Ask business questions together, do not ask the owner to pick frameworks. Keep a durable IMPLEMENTATION_STATUS.md. If context becomes short, update it before stopping.
