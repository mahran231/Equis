# Data model and security contract

Design contract, not runnable SQL. Claude Code must generate ordered SQL migrations, constraints, indexes, grants and policy tests from it. Never apply this prose as a production migration. Use UUIDs, UTC timestamptz for instants, date for local calendar dates, bounded numerics for measures and explicit units. Sensitive free text is minimized. All private tables have created_at/updated_at and authorized audit where appropriate.

## Logical schema
- `profiles`: id FK auth.users, display_name, locale, timezone, status(active/disabled). Users may edit only permitted self-service fields. Role/status never from client-editable metadata.
- `role_memberships`: user_id, role(owner/coach/client), granted_by/at, revoked_at. No self-service writes. Initial owner created securely once, all later changes authorized.
- `coach_assignments`: client_id, coach_id, starts_at, ends_at, assigned_by. One active primary coach per client for base scope. Assignment history preserved. Owner-only mutation.
- `programs`: id, client_id, package_code, package_version, starts_on, ends_on, status, freeze_allowance_days, timezone, version. No charging logic. Dates explicitly assigned.
- `program_freezes`: id, program_id, starts_on, resumes_on, approved_by, reason_code, created_at. Constraint resumes_on>starts_on; transaction checks no overlap and allowance. Do not expose private reasons in notifications.
- `intake_forms`, `checkin_forms`: id, version, owner_id, schema_json with field IDs/type/constraints/branching/visibility, status. Only approved immutable version assigned.
- `form_assignments`: id, client_id, form_id/version, due_on, status. `form_submissions`: id, assignment_id, client_id, answers_json, submitted_at, supersedes_id. Record version; validate answers server-side against that version. Drafts private.
- `coaching_analyses`: id, client_id, content_ref, version, status, approved_by, approved_at. Publication gate checks this row, not a checkbox from client input.
- `exercise_library`: id, stable_code, name_en, category, equipment, approved instructions, media_refs, variant, approved_by, archived_at. `recipes`: id, title_en/ar, steps, portions, ingredients_json with grams/raw_cooked/source, nutrient totals/source, approved_by, media_ref, archived_at.
- `plan_drafts`: id, client_id, program_id, week_start, version, document_json, analysis_id, updated_by. Mutable only by assigned coach, concurrency token required.
- `plan_versions`: id, client_id, program_id, week_start, revision, schema_version, snapshot_json, published_at/by, supersedes_id, content_hash. Immutable. Unique(program_id,week_start,revision). `plan_publications`: client/program/week -> active version pointer, changed transactionally.
- Snapshot contains exactly seven dated days, meal items with stable item IDs and nutrient sources, workout sessions and exercise prescriptions with stable IDs, mobility/warm-up, targets, notes and layout metadata. References to library IDs also preserve approved display values/media version so historical exports do not change when a library is edited.
- `meal_logs`, `workout_sessions`, `exercise_set_logs`, `mobility_logs`: id, client_id, plan_version_id, item/session/exercise_id, local_date, actual values+units, status, idempotency_key, occurred_at, recorded_at, revision. FKs/validation ensure logged item belongs to that client/version. Set logs unique(session_instance_id,exercise_item_id,set_index). Explicit repeated workout instance IDs avoid collapsing two legitimate sessions.
- `measurement_entries`: id, client_id, measured_on, weight_kg optional, body measures with explicit cm units, source(self/coach/file), recorded_by. Never auto-extract InBody values without review.
- `upload_requests`: id, client_id, requested_by, kind, purpose, due_on, status. `uploads`: id, client_id, request_id, category, object_key, detected_mime, size_bytes, checksum, scan_status, consent_id, uploaded_at, reviewed_at/by. Personal photos require request+consent. No permanent public URL column.
- `change_requests`: id, client_id, plan_version_id, item_id optional, reason, status(pending/reviewed/declined/resolved), response, resolved_version_id. Resolved requires actual published version or explicit no-change outcome.
- `coach_private_notes`: id, client_id, coach_id, text. Never serialized into client responses/exports.
- `conversations`: id, client_id, active_coach_id, status. `messages`: id, conversation_id, sender_id, body, sent_at, idempotency_key. Unique(sender_id,idempotency_key). `conversation_reads`: user_id, conversation_id,last_read_message_id. No global public Realtime topic.
- `notifications`: id, recipient_id, type, safe_payload, destination_ref, created_at, read_at, dedupe_key. `notification_preferences`: user_id, categories, quiet_hours, timezone. `push_subscriptions`: id,user_id,endpoint,keys,revoked_at; restricted as sensitive credentials. `notification_jobs`: scheduled_at,dedupe_key,status,attempts,next_attempt_at,expires_at. Worker-only transitions.
- `pdf_jobs`: id, client_id, requested_by, source_version/date_range, status, object_key, checksum, error_code, timestamps. `audit_events`: actor,target/action,result,timestamp,correlation_id with minimal metadata, no raw health content/tokens.
- `package_versions`, `public_content_versions`: draft/approved/published copy plus approver/time. `book_requests`: name, normalized_phone, consent_version, status, received_at, delete_after. `consents`: subject_id/pseudonymous request reference, purpose/version, granted/withdrawn_at. `data_requests`: requester_id,type,status,approved_export_ref/deletion_ticket. Separate health-record lifecycle from lead cleanup.

## Authorization matrix
Anonymous: read published public copy only; create rate-limited book request via validated server action, never select the requests table. No private table grants.
Client: own allowed profile columns; own active published plan/history assigned to them; own logs/forms/measurements/uploads/chat and notification preferences; cannot mutate prescriptions, assignments, roles, review/audit flags or other recipients.
Coach: assigned clients only while active and authorized; author/review permitted objects, not owner-only roles/content/payment policies. Coach-only notes kept separate.
Owner: explicit owner policies and audited administrative actions. Do not make every authenticated user an owner or every coach organization-wide admin.
Worker: specific server operations only; never trusts a browser-provided client_id, role, object_key, amount or recipient without reauthorization.

Implement RLS on every exposed table, least-privilege grants, per-operation USING and WITH CHECK, constrained functions and schema exposure. Guard joins and dependent rows too, not just parent client table. Profile-column updates require column grants/RPC validation because row ownership does not limit columns. Security-definer functions must fix search_path, avoid unsafe dynamic SQL, revoke public execution and check actor; test for recursive policies. Validate against actual Supabase version.

## Storage
Private buckets for health uploads, reports and client plans. Public bucket only for approved brand assets with no client data. Object keys generated server-side under client UUID/random UUID; authorization derives from database relation and active assignment, not path guessing alone. MIME sniffing/size/extension allowlist, malware scanning/quarantine and image re-encoding/EXIF stripping where possible before visibility. Proposed caps: images 10 MB, PDFs 20 MB; owner may change safe limits after testing. Reject SVG/HTML/executables and unsafe embedded content. HEIC support must be explicitly implemented/tested or explain how to convert, not silently fail on iPhone.

Use authenticated downloads when possible. If short-lived signed URLs are necessary, explain they are bearer links valid until expiry and may remain usable briefly after disable/reassignment. Proposed TTL <=60 seconds for health media, no logging URLs, no public caching. If immediate revocation is required, proxy authorization for every request instead. Validate object ownership before signing; never sign arbitrary submitted paths. Storage backup separate from database metadata.

## Threats and mandatory evidence
Direct object reference attacks across clients/coaches; self-role escalation; disabled but still-valid JWT; stale signed URL; cross-client CDN/query cache; malicious upload/polyglot; CSRF on cookie mutations; XSS in chat/form answers; SQL injection; recovery-link hijack; service-key leak; public realtime topic; PDF job ID guessing; job webhook forgery; duplicate retry; concurrent publish; overbroad export. For each, write a negative test and document the actual defense. Secure headers/CSP/TLS, dependency scanning, log redaction and endpoint rate limits are required. Never claim HIPAA/GDPR or Egyptian/Gulf legal compliance without a qualified review and applicable facts.

No real client records, health files or secrets belong in git, screenshots for public documentation, build fixtures or third-party telemetry. Synthetic fixtures may test the app but must be labeled and contain no reused actual client information.
